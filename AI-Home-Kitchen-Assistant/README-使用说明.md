# AI Home Kitchen Assistant｜预算优先与库存拍照版

本 ZIP 初始默认港币（HKD/HK$），包括周预算、菜单成本、采购清单及会员和上门服务展示。会员与上门服务统一固定显示港币，不随 IP 切换成美元或人民币；IP 只用于视频及购物平台等地区推荐。旧预算及历史预约不强制换币种。会员内部人民币基准仅用于汇率换算，不是界面显示币种。

## 本版新增：会员、菜品成本与 Home Chef

- 规划、一周食谱和采购页的页头右上角均提供同款会员／全功能试用按钮，点击可打开会员面板。试用剩余天数、到期状态和 Plus 升级通过同一份本地状态同步，包含同浏览器不同标签页。

- 会员和 Home Chef 参考价格统一在 `config.js`；Plus 基准 ¥12/月、Basic ¥8/月。做饭阿姨包月按每周5天、约22次/月设置：内地采用上海机构公开参考价 ¥2,200/月（每次2小时）；香港按 ERB 家常煮食参考时薪中值 HK$115、每次3小时估算 HK$7,590/月，参考区间 HK$7,260–7,920。页面附报价依据，均非平台的实际成交报价，食材、交通及节假日费用另确认。
- `state.js` 统一保存会员、周预算、采购、菜单、库存和预约；Demo 状态使用 localStorage，刷新后仍保留。
- 首次使用自动开启 7 天全功能试用：全部 Plus 功能、语音需求生成、库存拍照入口、AI 补购、高级预算优化及 Home Chef Demo 预约流程均可体验。实际 AI 和照片识别仍取决于后端支持，支付和商家连接仍为 Demo。试用不包含免费实际厨师服务，上门服务单独计费。
- 7 天从首次使用开始计算，刷新、切换页面及点击试用按钮不会重新计时；Demo 通过浏览器 localStorage 记住试用起点，真实产品需接入账号与服务端鉴权。到期后恢复 Basic：手动填写可继续生成基础食谱；语音需求生成及其他 Plus 功能需要升级。
- 会员固定使用港币，依据 ECB 日参考汇率换算人民币内部基准；Home Chef 固定显示香港参考价（如包月参考HK$7,590），不会根据 IP 改成美元。汇率失败则用缓存或标明 Demo 估算。预约保存确认时的币种、金额、次数及每次时长；旧预算和历史预约不被强制改币种。配置中仍保留其他地区参考资料供后续扩展。
- 菜卡显示预计成本；「查看做法」包含真实餐图、用餐人数、食材、采购状态和图文步骤。
- 在食谱详情点击「已购买」会同步移动到采购页的已购区域，并更新实际支出及剩余预算。
- Home Chef 为 Plus 预约资格，服务费仍按次或套餐另计；所有支付与预约均明确标记为 Demo。
- 第三方采购平台目前只显示示例入口；未来合作分成比例保留为 `partnerCommissionRate`，不会向消费者额外收费。
- 规划页快捷入口顺序为「用现有食材做饭／语音说需求／我的计划偏好」；偏好区默认隐藏，点击快捷按钮才展开。底部对话输入框常驻，发送需求后才显示助手回复；临期提醒作为页面最后一个内容区。首页左上角的小厨师图标已移除。
- 每顿饭和每道菜都会显示预计制作时间；「视频教学」会按 IP 地区推荐小红书、B站、抖音、YouTube、Instagram 或 TikTok，并可记住用户偏好。
- 「采购」支持「一键全部勾选」整周所有待购食材（再次点击可全部取消），也可按周一至周日的早餐、午餐、晚餐筛选；勾选后立即计算所选金额，再选择地区购物平台或打开附近菜场／超市地图。
- IP 地区查询失败时会自动使用设备语言和时区回退，不影响食谱与采购核心功能。

Demo 会员测试：在规划页右上角打开「会员 / Upgrade」，选择 Plus 后点击 `Simulate Upgrade`。页面会把本机 Demo 用户保存为 Plus；清除浏览器 localStorage 可恢复初始 Basic 状态。

## 使用方式

1. 解压 ZIP，进入 `AI-Home-Kitchen-Assistant` 文件夹。
2. 双击 `启动应用.command`，等待浏览器自动打开 `http://localhost:8765`。也可在终端运行 `python3 server.py`。直接双击 `index.html` 只能预览界面，无法保存 API Key 或使用 AI 接口。
3. 页面内先填写「每周预算」，再展开「我的计划偏好」设置用餐人员、身份、饮食偏好、忌口及每周各餐参与情况。
4. 点击快捷入口「🥕 用现有食材做饭」，打开库存模块后使用「拍照／上传现有食材照片」。手机端可直接拍照，电脑端可选择图片。已识别食材仍需人工确认，然后点击「保存已有食物」和「生成补购建议」。
5. 点击「🎙️ 语音说需求」，一次说完全家需求；手动点击「停止」后自动填写，也可编辑文字后点击「自动填写全家信息」。之后点击「我的计划偏好」核对所有成员。

## 各按钮及错误状态

- 「生成食谱 ➜」：提交当前预算、人员偏好、餐次、库存和可选补充要求，直接生成固定结构的一周菜单并跳转到「一周食谱」；不会继续追问非关键资料。
- 「用现有食材做饭」：展开/收起库存、拍照、食材识别、补购建议模块。
- 「AI 识别这张照片」：需要支持视觉输入的 AI API；未配置或失败时显示错误并允许手动输入。
- 「生成补购建议」：使用简单的本地示例规则（非完整个性化食谱），无库存时提示无法生成。结果需要自行核对忌口及数量。
- 「一周食谱」「采购与预算」导航：打开食谱与由当前菜谱配料汇总的采购清单。
- 语音识别依赖浏览器；不支持时显示提示，可手动输入。

## 后端配置 API Key

API Key 输入已从前端页面移除，只能由项目维护者配置在后端。复制 `.env.example` 为 `.env`，把 `API_KEY` 改成自己的 DeepSeek Key，再双击 `启动应用.command`。如需使用 OpenAI 或其他兼容服务，可直接修改 `.env` 中的 `API_PROVIDER`、`API_BASE`、`TEXT_MODEL` 和 `VISION_MODEL`。

Key 不会进入浏览器或前端代码，只由这台电脑上的 Python 服务读取。本机 `.env` 权限应限制为当前用户可读。**分享 ZIP 时必须排除 `.env`。**

如果页面提示厨房助手未连接，请先检查 `.env`，再重新双击 `启动应用.command`。

如果页面方式不方便，也可以复制 `.env.example` 为 `.env` 后填写 `API_KEY`。当前默认为 DeepSeek 后端：`API_BASE=https://api.deepseek.com`，对话与图片模型均为 `deepseek-flash`。也可在终端临时配置：

例如：

```bash
export API_KEY="你的私密密钥"
export API_PROVIDER="deepseek"
export API_BASE="https://api.deepseek.com"
export TEXT_MODEL="deepseek-flash"
export VISION_MODEL="deepseek-flash"
python3 server.py
```

启动后可访问 `http://localhost:8765/api/status` 检查配置状态。「生成食谱」通过后端 `/api/generate-menu` 生成固定菜单数据并写入食谱页，浏览器不会接触 API Key。

手机端选择拍照时需要用户授权。照片识别不能准确推断数量、食物新鲜程度或过敏原；请务必人工核对。

## 实现状态

已实现：前端交互、人员独立档案与餐次设置、预算输入、库存拍照/上传、持续语音转写、多人需求补全、手动食材录入、个性化一周菜单、从每道菜的结构化配料汇总采购清单、食谱变更后联动采购数据、目标预算规划、真实餐图匹配、采购清单及预算统计。视觉模型识别和菜单生成需要配置 API；实时商超价格与真实购物平台集成尚未完成。

默认家里已有大米、食用油、酱油、糖和食盐，每周预算只计算本周新买的蔬菜、肉、蛋、奶和水产等食材；不默认已有面条、面粉或其他主食。普通网络或生成异常不会清空资料，也不会要求重新验证，只有 API Key 确实未通过认证时才提示更换。

预算按“目标使用额”处理：系统会把菜谱所需食材的预计采购额安排在本周预算的 92%–98%，不会再为凑预算添加与菜谱无关的“升级组合”。实际采购价格仍需在清单中按小票修正。

食谱卡片会按菜名从 Wikimedia Commons 匹配自由许可的真实餐图，由后端下载到 `assets/dish-photos` 后再显示，不直接依赖外网图片热链；页面保留图片来源链接。未匹配到或无网络时，使用项目内 AI 生成的真实食物摄影兜底图，不再显示漫画盘子。

## 已合并页面

- `index.html`：规划、家庭资料、库存、语音及对话入口。
- `weekly-menu.html`：按日期查看早午晚餐，可选中、更换或删除菜品；修改会保存在本机浏览器。
- `shopping-budget.html`：待采购与已购买清单、食材编辑、预计与实际支出、预算进度；规划页预算会通过本机浏览器同步。
- 三个页面通过底部导航互相切换。AI 生成的每道菜保存结构化配料；采购页仅汇总当前已选菜品所需食材。取消、删除或更换菜品后，采购数据会同步更新。

## 后续合并与输出规范

1. 用户可见反馈必须像贴心的厨房助手：简短、自然、明确，不使用“已解析参数”“生成成功”“模型输出”等生硬技术术语。
2. AI 原始结果不得直接展示。模型结果必须先转换为固定菜单数据结构，再经过系统检查与整理，确认成员、餐次、忌口、预算和必填字段完整后才能进入页面。
3. 标准处理流程：用户需求 → 系统识别并确认 → AI 生成原始菜单 → 系统检查与整理 → 生成自然短回复和食谱页面数据 → 用户查看结果。
4. 校验失败时只向用户说明需要补充或调整的内容；技术错误、提示词、原始 JSON、模型推理及未整理文本不得出现在用户界面。
